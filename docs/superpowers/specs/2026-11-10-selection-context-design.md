# 划词解释/追问的局部上下文 · 设计文档

- 日期：2026-11-10
- 状态：已批准（用户要求设计后直接实现）
- 范围：划词「解释 / 追问」与 Alt+Q 选中解释；不改翻译队列、翻译提示词、内容脚本渲染规则
- 相关代码：`src/content/selection.ts`、`src/content/main.ts`、`src/background/index.ts`、`src/panel/main.ts`、`src/background/dispatch.ts`

## 1. 为什么做

当前划词请求只把选中文字和页面标题/URL 发到侧边栏，另外附带“最近 5 个已翻译段落”。当用户在某一段落中选中一句时：

- 页面未翻译：模型只有标题、URL 和选中句，缺少句子所在段落。
- 页面已翻译：最近 5 段可能来自页面别处，不一定是选中句所在段落。
- 选中句所在段落的原文、前一句、前一段没有离开页面。

结果是指代词、转折句、术语缩写等经常无法被正确解释。

## 2. 目标

- 用户点击「解释」或「追问」时，抓取选中句附近的原文，作为辅助上下文。
- 上下文在划词动作发生时抓取，和选中文字一起进入侧边栏；不额外发起网络请求。
- 侧边栏把上下文放进 `ChatContext`，由后台拼进用户消息，不进入 system prompt。
- 页面未翻译也能工作；不依赖“最近 5 段翻译”。
- 上下文有明确长度上限，避免长页面撑爆 token。
- 不影响原有翻译、翻译队列、并发/重试、页面 DOM 规则。

## 3. 非目标

- 不抓取整页正文或整篇文章。
- 不做页面摘要、RAG、向量检索。
- 不读取 iframe 内部选区（内容脚本仍只跑顶层 frame）。
- 不把上下文写入聊天历史；只在带引用的这次请求中发送。
- 不改变侧边栏已有的“最近已翻译段落”能力，两者可以并存。

## 4. 方案比较

### 方案 A：划词时在内容脚本抓取（采用）

在 `selection.ts` 拿到 `Range` 快照，传给内容脚本的 `sendOpenChat`。内容脚本计算当前段落、最近两个前置段落和最近标题，随 `open-chat` 消息发送。后台把上下文存进 `chat.pendingQuote`，侧边栏读取后塞进 `ChatContext`。

优点：抓取时机最准确；页面未翻译也能用；无需侧边栏再向内容脚本要一次数据；失败可降级为空上下文。

缺点：需要在内容脚本里做块级元素启发式判断。

### 方案 B：侧边栏打开后再向内容脚本请求

后台只存选中文字，侧边栏再发 `get-selection-context` 消息。缺点：面板打开有延迟，选区可能已经变化；多一次消息往返；失败路径更多。

### 方案 C：继续只用最近翻译段落

改动最小，但无法解决“选中句所在段落未被翻译”或“最近 5 段不相关”的核心问题。

结论：采用 A。

## 5. 数据结构

```ts
export interface SelectionContext {
  /** 最近的上级标题，纯文本，最多 120 字。 */
  heading?: string;
  /** 选中句所在块级段落的原文，最多 1000 字；超长时围绕选区截取。 */
  paragraph: string;
  /** 选中段落之前最多 2 个块级段落的原文，按从远到近排列，每段最多 500 字。 */
  preceding: string[];
}
```

`OpenChatMessage` 增加可选的 `context?: SelectionContext`。
`ChatContext` 增加可选的 `selectionContext?: SelectionContext`。
`chat.pendingQuote` 增加可选的 `context`。

## 6. 抓取规则

1. 从 `Range.startContainer` 向上找最近的块级元素：
   `p, li, blockquote, td, th, dd, dt, figcaption, pre, h1-h6, div, section, article`。
2. 用 `extractSourceText` 取该元素原文，并去掉 `.ilmt-tr` 译文节点。
3. 空白折叠为单个空格。
4. 如果段落超过 1000 字：
   - 找到选中文字在段落中的位置；
   - 以选区为中心取窗口，优先保留前文（约 600 字），后面保留约 300 字；
   - 截断处加 `…`。
5. 前置段落：从当前段落向前找同级块级元素，最多 2 个；跳过空段和纯译文。
6. 标题：向前/向上找最近的 `h1-h6`，取纯文本，最多 120 字。
7. 选区为空、找不到块级元素、或段落为空时返回 `undefined`，不阻塞划词。

## 7. 发送与展示

- 内容脚本：`sendOpenChat(text, mode, range)` 计算上下文并发送 `{ type: "open-chat", text, mode, context }`。
- 后台：把 `context` 原样存进 `chat.pendingQuote`。
- 侧边栏：
  - 解析并校验 `context`；
  - 「解释」自动发送时带上 `context`；
  - 「追问」预填时保留 `context`，用户发送时一并带上；
  - 重试时保留最近一次 `selectionContext`。
- 后台 `buildPageContextBlock` 增加：

```text
【选中位置上下文】
所在标题：...
前面段落：
- ...
当前段落：
...
```

然后才输出原有的最近翻译段落和选中引用。

- 侧边栏顶部提示从「只参考已翻译的段落」改为「参考选中段落与已翻译内容」。

## 8. 长度与隐私

- 只在用户明确点击「解释 / 追问」或按 Alt+Q 时抓取。
- 不做后台扫描，不自动上传整页。
- 上限：当前段落 1000 字、每个前置段落 500 字、标题 120 字、前置段落最多 2 个。
- 上下文只进入用户消息，不进入 system prompt。

## 9. 测试

- 内容脚本上下文：
  - 选中句所在段落 + 前置段落 + 标题。
  - 译文节点不会混进原文。
  - 超长段落围绕选区截断。
  - 选区为空/找不到段落时返回 undefined。
  - 嵌套 inline 元素中的选区仍能找到段落。
- 划词气泡：回调能拿到 `Range`，关闭气泡不丢失上下文。
- `open-chat`：context 被写入 pending quote。
- 侧边栏：解释自动发送、追问预填、重试都保留 context；页面失效时不发送旧上下文。
- 后台 prompt：`【选中位置上下文】` 出现在用户消息，不进入 system prompt，问题只出现一次。
- 全量 `npm test`、`npx tsc --noEmit`、`npm run build`、`node scripts/check-build.mjs`。

## 10. 风险

- 块级元素识别是启发式的：复杂站点可能把多个段落放在一个 `div` 里；用长度上限和窗口截断保证可用。
- 选区跨多个段落时只取起始段落；这符合“从某一句发起解释”的主要场景。
- 页面结构在面板打开前变化时，上下文可能已过期；本次请求仍使用抓取时的快照，和选中文字保持一致。
